# Solvelt design system

## Principles
1. Calm and trustworthy: auth screens do one thing; the primary action is always the strongest element.
2. Never lose input; say what to do next in plain words.
3. Accessible by construction: 44px targets, visible focus, labels, errors with icon+text+`aria-live`, reduced motion.
4. Small footprint: no UI framework, self-hosted latin-subset fonts with metric-matched fallbacks (no third-party requests, no layout shift), inline SVG icons.

## Tokens (`src/styles.css`, `:root`)
- Colour: `--bg --surface --surface-2 --fg --muted --border --primary --accent --err --ok …` Light by default; dark via `prefers-color-scheme` and `[data-theme=dark]`. A manual toggle persists to `localStorage` (`solvelt-theme`); an inline script in `index.html` applies it before paint.
- Type: fluid `--fs-sm … --fs-2xl` using `clamp()`; `--font` (Plus Jakarta Sans) and `--font-display` (Playfair Display), see "Figma restyle" below.
- Spacing: 8-pt grid `--s1…--s8` (plus a 4px half-step). Radius `--r-*`, shadow `--shadow-*`, motion `--t-*`/`--ease`.

## Components (`src/components/ui.tsx`)
Button (primary/secondary/ghost/destructive, loading), Field (label, hint, error), PasswordField (show/hide) + StrengthMeter, OtpInput, Checkbox/Select (styled natively), Card, Shell (brand panel + top bar), Alert (aria-live), Modal (idle/passkey dialogs), Stepper (`ProgressBar`, tracker), Skeleton, Spinner, Icon set, ThemeToggle, SettingCard (account page cards + status chips).

## Decisions
- Class names (`btn`, `field`, `alert`…) were kept so existing behaviour and 76 unit tests stay valid; styling and structure were redesigned underneath.
- OTP is one real `<input>` with a visual 6-cell overlay: paste, SMS autofill and screen readers work with no focus juggling.
- Marketplace look: seller panel (storefront mock-up + benefits) on desktop, "Start selling" / "Sign in" cross-link in the top bar, benefits strip above the wizard. Copy is placeholder, with no invented fees or numbers.
- Dependencies added: `@axe-core/playwright` (dev) and `uqr` (~tiny, no deps) so the 2FA QR is drawn locally. Icons are hand-inlined lucide-style paths rather than a package.
- Security behaviour untouched: token handling, CSRF, multi-tab coordination, 2FA prompts, step-up, redirect safety.
- Tests: `npm test` (Vitest), `npm run test:ui` (mocked-API Playwright + axe, light/dark, 390/1440), `npm run e2e` (real backend).
- Route-level code splitting: Settings and the authed wizard steps (business, kosher, review, pending) and Guest are `React.lazy` chunks behind one `Suspense` spinner.
- Theme bootstrap lives in `public/theme.js` (external script) so it works under a strict `script-src 'self'` CSP; `ThemeToggle` also reads the saved choice itself. Covered by a Vitest test and a CSP-header UI test against the production build.
- `ErrorBoundary` wraps the lazy routes: a chunk-load failure after a deploy shows a "Reload" card instead of a blank page.
- Signed-in pages render a single header (`AppHeaderContext` tells `Shell` not to add its own logo + theme toggle).

## Phone number, Phone PIN and texted links
- Settings → Security has a **Phone number** card (add or change with a texted code, remove) and a **Phone PIN** card (set or change, with the same strength rules as the server: 6 digits, no repeated digit, no sequence, no repeating pattern; `src/lib/pin.ts`). Both use `SettingCard`, `Field`, `PasswordField`, `Alert`; code in `src/pages/PhoneSettings.tsx`.
- Step-up is the server's: password for password accounts; otherwise a code (emailed while there is no number yet, texted to the current number afterwards). Field labels are unique on the page (`Password to confirm`, `Password to confirm PIN change`) so assistive tech and tests can tell the cards apart.
- `/l/<token>` (`src/pages/PhoneLink.tsx`) is the landing page of the links we text. A reset link redeems once (shared in-flight request, StrictMode-safe) and continues to `/reset-password`; a phone sign-up link shows "Finish creating your account" (email, password, Terms) and continues to email verification; anything else explains that the link is invalid, expired or used.
- Tests: `src/pages/phone.test.tsx` (Vitest), mocked-UI Playwright screens with axe in light/dark and mobile/desktop (`settings-phone-add`, `settings-phone-set`, `phone-link-finish`, `phone-link-expired`), and real-backend `e2e/phone.spec.ts` (signed SMS webhooks against the Testing backend; needs `Phone__Enabled=true`, set in `playwright.config.ts`).

## Teams, roles & brands (feature D)
- **Account model in the UI:** `useAuth()` exposes `user.accounts`, `user.activeAccountId`, `user.role`, `switchAccount()` and `refreshAccounts()`. `accounts === null` means an old server without accounts (no gate is shown). The access token carries the active account; the server re-validates the membership on every request.
- **Account picker / empty state** (`pages/teams/ChooseAccount.tsx`): shown by `RequireAuth` whenever the user has no active account (several accounts, or none); exactly one account is opened automatically. Also at `/accounts` (reached from the switcher's "All accounts" / "Create a new seller account"). Pending invitations (Accept/Decline) and "Create a new seller account" (terms checkbox) live on the same screen. A `403 no_active_account` from any call (membership removed) triggers `refreshAccounts()`, which brings the user back here.
- **Switchers** (header): `AccountSwitcher` (current account + role badge, list, create, all accounts) and `BrandSwitcher` (a "Brand" filter, only when ≥ 2 brands; remembered per account in `sessionStorage`; read it with `useBrands()` in product screens later). The page tree is keyed by the active account, so every screen reloads after a switch.
- **Settings → Team / Brands** are tabs in the existing Settings page (lazy chunks). Team: Owner/Admin only (Owner also sees Transfer ownership and **Close this account**: a warning dialog with a confirmation checkbox and step-up re-authentication; after a transfer or a close the app re-reads the account list so badges, cards and row actions follow the new role); members table that becomes cards below 720px (explicit ARIA table roles keep it a table for assistive tech), invite / change role+scope / remove / leave / transfer ownership dialogs, pending invitations with resend/revoke. Brand logos are only fetched when the URL is our own `/api/…` path (the bearer token is never sent elsewhere). Brands: everyone can look, Owner/Admin manage (add/edit with logo preview and client-side type/size checks, archive/restore; the last active brand can't be archived). Actions the role can't do are **hidden**; the server remains the authority (`lib/teams.ts` mirrors the permission matrix for hints only).
- **Dialogs:** `components/Dialog.tsx`: labelled, focus moves in and returns, Tab is trapped, Escape closes. Role descriptions are plain-language (`ROLE_DESC`).
- **Invite pages** (`/invite/:token`, public): states pending / expired / revoked / used / declined / unknown; signed out → join form with the email pre-filled and locked (no seller wizard; the link proves the mailbox) or "I already have a login"; signed in → Accept / Decline, and a clear "wrong email" screen with sign-out. Non-owner members land on the product catalog (`/products`; they don't fill in the seller application). **The invitation token is a credential:** `/invite/:token` immediately REPLACES itself with `/invite` (token kept in router state and `sessionStorage`), so it is never left in history, copied into `/login?next=` or forwarded as a provider `returnUrl` (server logs); it is cleared once the invitation is used, declined, expired or invalid.
- **Buttons with context** use a visible short label plus an `sr-only` suffix (e.g. "Remove" + " dov@example.com") so the accessible name contains the visible text (WCAG 2.5.3).
- **Tests:** Vitest `pages/teams/teams.test.tsx` (picker, switchers, Team, Brands, invite states), mocked Playwright + axe `e2e-ui/teams.ui.spec.ts` (9 screens × 390/1440 × light/dark, screenshots with `SHOTS_DIR=docs/screenshots`), real-backend `e2e/teams.spec.ts` (invite → join → scoped view, two accounts → picker → switch, removal denied on the next action, 320px dark mode), each with axe.

## Seller products (workstream B)
Code: `src/products/**` (lazy routes `/products`, `/products/new`, `/products/import`, `/products/:id`, `/questions`), styles in `src/products/products.css` (class names are `p`-prefixed where the global sheet already had a name). Backend contract: backend `docs/PRODUCTS.md`.

### Structure and decisions
- **Shell:** `SellerLayout` (route-level, lazy) puts a sidebar (Products, Bulk upload, Questions, Account & security, plus Team/Brands for Owner/Admin) under the app-wide header that `RequireAuth` renders. The header, account and brand switchers are D's and are untouched. On screens < 900 px the sidebar becomes a "Menu" drawer (button with `aria-expanded`, Escape closes and returns focus).
- **Active brand:** the header's `BrandSwitcher` (`useBrands()`) is the only brand filter of the catalog (`brandId` query); the "Add product" step and editor preselect it. The editor still offers a brand `<select>` when the member can write to several brands. Viewer = read-only everywhere (`useCanWrite`: disabled fields, no add/bulk/duplicate/delete/activate); the server enforces the same (403/404).
- **Progressive disclosure:** the "What are you selling?" step asks only for a title and a category. The editor is one page with a sticky section navigator (left on desktop, scrolling chips on mobile) and a score/checklist panel. Advanced fields are revealed only when relevant: condition notes for non-new items, sale price + dates behind "Put this product on sale", variations behind "This product comes in different options", barcode input hidden by "no barcode", stock extras / cost under "More stock and cost options", SEO under "Advanced", category details only after a category is chosen, return conditions only when returns are allowed.
- **Data-driven details:** `Details.tsx` renders `attributeConfig` from the server (text, longtext, number + unit, select, multiselect, bool; grouped; required marked). Changing the category clears the old values at once and fetches the new config; the server also drops values that do not belong.
- **Autosave:** `useAutosave` (1.2 s debounce, serialised, one follow-up save if edits arrive mid-save). Indicator text: "Saving soon…", "Saving…", "All changes saved", "Couldn't save" (with Retry; input is never discarded, 400 field errors are shown inline). Everything the editor sends to the server goes through one promise chain (`enqueue`) so a save never races an image upload on the row-version token. Active (live) listings use an explicit "Save changes" button because they must stay publishable (the server answers 422 otherwise). `409 version_conflict` offers "Keep my version" or "Load the latest".
- **Unsaved-changes guard:** `beforeunload` plus a document-level capture of in-app link clicks (BrowserRouter has no blocker API) opening "Save and leave / Leave without saving / Stay". It also covers header and sidebar links we do not own.
- **Media:** drag-and-drop or file picker, per-file progress (XHR), client pre-checks (type, 10 MB, max 9), reorder by drag or with ← / → buttons (keyboard), "Set as main", alt text per photo, low-resolution warning. Protected images are fetched with the bearer token into object URLs (`AuthImage`) because `<img>` cannot send `Authorization`.
- **Description:** up to 5 bullet inputs; Markdown textarea with a toolbar and a live preview rendered to React elements (never `innerHTML`; same subset as the server's safe renderer). Tabs Write/Preview below 760 px.
- **Variations:** option names + chip inputs (paste a comma list), combination grid (on/SKU/price/stock/barcode/photo per row), "fill every row" shortcuts, limits 3 options / 20 values / 100 variations, existing row data is kept when options change. Per-variation photos use the same image manager.
- **Preview as buyer:** a dialog rendering the live (unsaved) form as a shopper would see it: gallery, title, brand, price with compare-at and sale, condition, variation selectors that switch photos and price, stock, bullets, shipping and returns line, description, details table, Q&A.
- **Quality:** the panel shows the server score (0-100: Needs work / Good / Great) and "Ready to publish?" with required items (each button scrolls to and focuses its field) and a collapsed list of suggestions. List badges use the same buckets (colour + word + number, never colour alone).
- **Catalog list:** status tabs with counts (All, Drafts, Active, Inactive, Archived, Out of stock, Needs attention), debounced search, sort, pagination, skeleton, friendly empty state, table on desktop / cards on mobile, inline price and stock editing (blur or Enter saves, Escape cancels, errors revert with a message), bulk activate/deactivate/archive with per-listing failures reported, duplicate.
- **Questions inbox**, **Bulk upload** (template download, drop zone, validation preview with row-level errors, import as drafts, catalog export) follow the same cards/alerts patterns.
- **Standards:** one `h1` per page, labelled controls, 44 px targets (36 px inside dense grids, still ≥ WCAG 2.2 target size), visible focus, `aria-live` status/errors, `prefers-reduced-motion` honoured, light/dark via tokens only, responsive from 320 px (no horizontal page scroll, tables scroll inside their wrapper), route-level code splitting (`ProductEditor` chunk ~17 kB gzipped).
- **Tests:** Vitest (`src/products/*.test.tsx`: sections, attributes + category change, checklist, barcode, variations grid, autosave, unsaved guard, list filters, quick edit, bulk, questions, CSV, shell, roles), mocked-UI Playwright + axe in light/dark at 390 and 1440 px plus a 320 px overflow check (`e2e-ui/products.spec.ts`), real-backend Playwright (`e2e/products.spec.ts`: create with photos, bullets, variation and specs → preview → activate → list → inline price edit; pending seller can draft but not activate; answer a question; CSV import; axe on every page).
- Screenshots: `docs/screenshots/products-*.png`, `product-*.png`, `questions-*.png`, `bulk-upload-*.png` (desktop + mobile; the editor also in dark).
- **CSP and inline styles (verified, not assumed):** React applies `style={{…}}` through the CSSOM (`element.style`), which `style-src` does not block; only `style` attributes in HTML markup and `setAttribute('style')` are blocked. A UI test serves the production build with the README CSP and asserts the wizard progress bar and settings skeleton widths really apply with zero `securitypolicyviolation` events. The QR SVG is injected as markup but uses presentation attributes only (no `style`).
- **zod and `unsafe-eval`:** zod probes `new Function` to enable JIT validation; a strict CSP reports that probe as a violation even though the error is swallowed. `src/zodConfig.ts` sets `jitless` and is imported first in `main.tsx` (ES imports are hoisted, so setting it after the imports would be too late for schemas built at import time).


## Seller assistant (workstream H)
Code: `src/assistant/**` (`context.tsx` provider + state machine, `api.ts` REST + SSE reader, `AssistantPanel.tsx` button/drawer/history, `MessageView.tsx`, `ActionCardView.tsx`, `routes.ts` links/suggestions/page context, `assistant.css`). Mounted once in `RequireAuth` (keyed by the active account, so switching accounts resets the chat). Backend contract and safety model: backend `docs/ASSISTANT.md`.

### Decisions
- **Entry point:** an "Assistant" button in the app header (`aria-expanded`, `aria-controls`). It is not rendered at all while `GET /assistant/config` says `enabled:false` or the server has no assistant, and no account means no request. A kill switch (`stopped`) shows a banner and disables the composer and every Confirm button.
- **Layout:** a right-hand drawer (440 px, `role="dialog"`, non-modal) on desktop; below 700 px it is full screen and behaves modally (Tab is trapped, `aria-modal`). Opening focuses the composer; Escape closes and returns focus to the header button. Entrance animation only under `prefers-reduced-motion: no-preference`.
- **Streaming:** `fetch` + `ReadableStream` parse of the SSE events (`conversation`, `tool`, `text`, `action`, `error`, `done`), one retry through the single-flight token refresh on 401. The transcript is `role="log"` `aria-live="polite"` with `aria-busy` while an answer streams (screen readers get the finished text instead of every fragment). **Stop generating** aborts the request and keeps the text; **Try again** re-sends the last question; **Copy** copies one answer.
- **Tool activity:** each tool call appears as "Looking up your orders…" with a spinner, then a tick; stored conversations show the same summaries.
- **Action cards (the safety-critical UI):** summary, risk badge (text, never colour alone), before/after table (real `<table>` with row headers) and "Expires in N min. Nothing has changed yet." come from the server's card, not from the model's prose. Confirm sends the bearer token **and** `X-CSRF-Token`; a 409 `target_changed` replaces the card with "Replaced" and appends the refreshed proposal; expired, cancelled, failed (with the server's reason) and confirmed states remove the buttons. Buttons carry the target in an `sr-only` suffix ("Confirm Challah board").
- **Safe rendering:** answers go through the existing `Markdown` component with `links={false}` (React elements, no `innerHTML`; every `[label](url)`, nested ones included, renders as its label only, so nothing the model writes can become a link; the server cleans the text too). Links to entities are built only from `{kind, id}` in `routes.ts` (`/products/:id`, `/orders/:id`, `/bookings/:id`, `/messages/:id`, `/quote-requests/:id`; ids must look like GUIDs); the Orders/Services pages are other workstreams, until they land the app's catch-all sends those links home.
- **Context:** the route tells the server what "this listing" is (`page: {kind:'product', id}`); suggested prompts depend on the page and on the role ("Improve this listing" on a product, no change suggestions for Viewers).
- **History:** list, open, rename, delete one and "Delete all my history" (two-step confirm inline, no `window.confirm`); retention text comes from the config.
- **States:** empty (greeting + suggestions), loading (skeleton), error (alert + Try again), pre-flight server errors (budget, too long, unavailable) show the server's sentence.
- **Tests:** Vitest (`assistant.test.tsx`: entry point hidden/visible, focus and Escape, streaming with links/HTML/URL safety and page context, Confirm with CSRF header, Cancel, refreshed proposal, expired, forbidden, Viewer, kill switch, Stop, budget error + retry, history, SSE parser, route helpers) and real-backend Playwright (`e2e/assistant.spec.ts`: challah board -> card -> Confirm -> Draft exists; cancel changes nothing; late orders answer links to the order; Viewer sees no action buttons; phone full screen, dark mode; axe on every state). The Playwright backend uses the scripted fake model (`Assistant__Provider=Fake`), so real model quality is not covered.
- Screenshots: `docs/screenshots/assistant-card-desktop.png`, `assistant-answer-desktop.png`, `assistant-empty-mobile.png`, `assistant-card-mobile.png`.

## Seller orders and buyer messages (workstream E)
Code: `src/orders/**` (lazy routes `/orders`, `/orders/:id`, `/messages/:id?`, dev-only `/dev/simulator`, Settings → Notifications), styles `src/orders/orders.css` on top of the products sheet. Backend contract: backend `docs/ORDERS.md`.

- **Shell:** "Orders" and "Messages" are the first two entries of B's sidebar (`SellerLayout`), with badges: orders that need action and unread conversations. The badge is part of the link's accessible name ("Orders 5 need action", visible text "Orders 5", which satisfies WCAG label-in-name; found by axe). Counts refresh from the live stream and every 30 s.
- **Live updates:** `src/orders/live.ts` keeps ONE shared `fetch`-based Server-Sent Events stream (`GET /seller/events`, bearer header, since `EventSource` cannot send it), reconnects with backoff, and `useLiveReload` re-reads open pages (debounced; the order page never reloads under an open dialog). The 30 s count polling is the fallback when the stream is unavailable.
- **Orders list:** at-a-glance tiles (today, to ship, late, open returns, 30-day sales with an accessible mini chart, late-shipment and cancellation rates), tabs with counts (Needs action, Pending acceptance, Shipped, Delivered, Cancelled, Returns, All), search (number, buyer, SKU, tracking), "More filters" (dates, status, shipping speed, late, oversold), sort, pagination, table on desktop / cards on mobile with a ship-by countdown (text + colour, never colour alone), skeleton and friendly empty states. The header brand switcher is the brand filter. Bulk: accept, print packing slips, CSV tracking upload (template, row-by-row check with errors, then apply), CSV export. Everything is kept in the URL.
- **Order detail:** status + flags + the next best action in the header; items with photos/options/SKUs; shipments with tracking links (opens the carrier in a new tab with `noopener`); cancellation requests and returns with their decisions; refunds; message thread box with saved replies; timeline; payment summary (items, shipping, tax, discounts, fee, earnings); address with a Copy button; internal notes. The server tells the page what the caller may do (`actions`), so Managers/Viewers never see dead buttons.
- **Dialogs** (`Dialogs.tsx`, labelled, focus trapped, Escape closes, input never lost): ship (full or partial: per-line quantities, carrier, tracking format check, ship date, a label-purchase placeholder), edit tracking, cancel (reason list, note, restock switch; for a partly shipped order it cancels the unshipped items), cancellation request (approve with restock / decline with a note), refund (per-line quantities limited to what shipped, shipping amount limit, live total from the server's preview, the Manager limit message, then a separate "can't undo" confirmation), return reject (reason) / receive (restock switch), hold.
- **Packing slips:** rendered from data in the page (no external images or fonts) and printed through a `@media print` stylesheet that shows only the slips; gift orders hide prices.
- **Messages:** one inbox for order and pre-sale product conversations (filters Unread / Needs reply / Overdue, order-or-product, assigned to me, search). The conversation shows a chat thread with timestamps and delivery state, the order or product card with quick actions, saved replies (add/delete), image/PDF attachments (client hints only; the server sniffs the content), a contact-details warning with "Send anyway", assignment, "no reply needed" and internal notes. Drafts are kept in `sessionStorage` per conversation until sent. On narrow screens the list and the conversation are separate views.
- **Notifications:** Settings → Notifications has one switch per email kind, saved on change (rolls back with a message on failure).
- **Simulator:** `/dev/simulator` exists only in the Vite dev server (`import.meta.env.DEV`): test orders (single, several items, split brands, variants, out of stock), buyer events (cancel, return, delivered, message), a pre-sale product question and a view of what the marketplace received.
- **Standards:** one `h1` per page, labelled controls, 44 px targets, visible focus, `aria-live` status/errors, reduced motion, light/dark through tokens, responsive from 320 px, route-level code splitting.
- **Tests:** Vitest `src/orders/orders.test.tsx` and `messages.test.tsx` (list tabs/filters/bulk/CSV/packing slips, detail actions, partial ship dialog, refund limits and confirmation, returns, cancellation requests, roles, notes, messages, contact warning, drafts, attachments, badges, preferences); real-backend Playwright `e2e/orders.spec.ts` (simulator order accept → partial ship → ship rest → delivered; buyer cancel request approved with stock restored; return → approve → received → partial refund; Manager of brand X cannot see brand Y; Viewer cannot act; buyer message → saved reply + image → reply event in the dev sink; pre-sale question; CSV upload; notification settings) with axe on every new page and dialog; `SHOTS_DIR=docs/screenshots npx playwright test e2e/orders-shots.spec.ts` captures `orders-*`, `order-*`, `messages-*`, `settings-notifications-*` (desktop + mobile).

## Pending screen and landing by status
- **"Live" is not a status any more: Approved is the final, selling state.** The tracker is Sent → Review → Approved; once approved the last stage shows as done (check mark) and stays `aria-current="step"`. `src/lib/status.ts` (`normalizeStatus`) treats a stale `Live` from an older backend as `Approved` where a status enters the app (wizard load, `Home`, account lists/chips, Settings profile), so nothing breaks before the backend migration lands. `Live` is gone from the frontend status union.
- **Landing (`Home`)**: Owners whose application is `Approved` go straight to `/products`; every other status keeps `stepPath(app)` (wizard step or `/signup/pending`). Team members (non-Owners) still go to `/products` without loading the application.
- **`/signup/pending` is status-aware.** Undecided (`PendingReview`) shows "What happens next" plus a secondary link "Start preparing your products (saved as drafts)", because drafts are allowed while the application is in review. `Approved` replaces it with a "You're all set" card whose single primary action is **Go to your products**, and the copy "You're approved — your shop is open and you can publish products." "Visit marketplace" is always secondary (one primary action per page). `Rejected` and `Suspended` show no products links and no "What happens next" (it only applies while the application is being reviewed): Rejected gets "Think we got this wrong?" (contact support to ask for another look), Suspended gets "Your account is paused" (contact support). No support address is invented in the UI. `Suspended` keeps the tracker on Approved (not done) with the error alert.
- `NeedsInfo` never reaches this page: `WizardLayout` sends it back to the business step, so its branch here is defensive only. That also means a `NeedsInfo` owner has no link to `/products` from the UI.
- Tests: `src/pages/wizard.test.tsx` (per-status pending screen, 3-stage tracker, stale `Live`), `src/pages/home.test.tsx` (landing), `src/pages/teams/teams.test.tsx` (stale `Live` in the account list), `e2e/portal.spec.ts` (real backend: `/` lands on `/products`, pending page still reachable), and mocked-UI screens `pending-approved` / `pending-stale-live` with axe and screenshots.



## Services, calendar & bookings (workstream F)
Code: `src/services/**` (lazy routes `/calendar`, `/bookings`, `/bookings/:id`, `/bookings/quotes/:id`, and Settings → Availability at `/settings/availability`), styles `src/services/services.css`. Backend contract: backend `docs/SERVICES.md`.

- **Catalog:** services share the products catalog. "Add" starts with a Product / Service picker; the list has a Type filter and shows the service rate in the price column. The service editor adds sections (Service, Where, Pricing, Booking rules, Intake questions, Policies, Providers) revealed progressively: service area only for "at the customer's location", travel fee/buffer only there, hourly rate vs fixed price vs quote-required. Autosave and the version token are shared with the product editor; the status indicator merges both save streams (error > saving > dirty > saved).
- **Calendar:** day, week, month and list views. Each member who provides services has their own calendar, plus a combined view. The month grid is a roving-tabindex grid (arrow keys); the week grid shows events as buttons whose visible text is contained in the accessible name (WCAG 2.5.3, extra detail in `sr-only` text). The list view is the non-visual/keyboard alternative to the grids. Times are rendered in the provider's time zone using `Intl.DateTimeFormat` (no date library), DST-safe.
- **Availability:** weekly hours as local intervals, date overrides, buffers, notice, booking window, granularity, instant vs request-to-book, blocks and ICS feed links. Number inputs keep what was typed (`NumField`).
- **Bookings:** status tabs, request queue (approve / decline / propose another time), detail page with timeline, messages, reschedule, cancel (policy fee preview), start / complete (extra hourly time creates an additional-charge request) / no-show, reassign. Customer details appear only once a booking is confirmed (server-enforced; the UI mirrors it).
- **Time pickers:** propose/reschedule dialogs show the free start times of the chosen day, asked from the server per booking (`GET /seller/services/{id}/slots?bookingId=…`): the server uses the booking's own duration (add-ons included), its location and the provider's calendar without the booking itself, and applies notice rules only where the real move does, so the page sends nothing but the booking id. Times are toggle buttons that fill the time field and carry the exact instant (on the day the clocks go back the two 01:30 slots read "01:30 EDT" / "01:30 EST"); typing a date or time drops the picked instant; an empty date says so instead of loading forever. The quote composer still uses typed times (the engine rejects availability queries for quote-priced services). After an action whose button disappears, focus moves to the next action or the page heading. Message times use the provider's zone.
- **Quote requests:** list and composer (price, validity, note); accepted quotes become bookings.
- **Standards:** same as products: one `h1`, labelled controls, ≥ 24 px targets, focus visible, `aria-live` status, light/dark tokens, responsive from 320 px (tables scroll inside `.tablewrap` or turn into cards), route-level code splitting.
- **Tests:** Vitest + MSW (`src/services/*.test.tsx`), mocked-UI Playwright with axe at 390 / 1440 px, light and dark, plus a 320 px overflow test (`e2e-ui/services.spec.ts`), and real-backend Playwright (`e2e/services.spec.ts`: create service and provider, set availability, book via the simulator, approve, reschedule, complete, quote flow).

## Staff admin area (workstream G)
Code: `src/admin/**` (one lazy route, `/admin/*`, its own CSS chunk `admin.css`). Backend contract and permission matrix: backend `docs/ADMIN.md`. It is **not** part of the seller app: no seller sidebar, no seller header, no account/brand switchers.

### Decisions
- **Separate session, in memory only.** `src/admin/api.ts` keeps the staff token in a module variable, never in storage, and never touches the seller `tokenStore`, refresh cookie or CSRF cookie (`credentials: 'omit'`). Staff sessions have no refresh on the server, so a page reload means signing in again; that is deliberate (short session, no standing credential in the browser).
- **Sign-in is two steps in one form** (`AdminApp.tsx`): email + password, then the authenticator code (or a recovery code). The server's answers are deliberately uniform, so the UI shows one generic failure message. An account with no second factor is taken through setup in place: QR (drawn locally with `uqr`) + manual key, first code, ten recovery codes shown once, then sign-in. `/admin/accept-invite` is the emailed link target (password for a new account, or the current password for an existing one).
- **Step-up is handled once, centrally.** `useAdmin().run(fn)` runs an action; if the server answers `403 step_up_required`, the shared `StepUpDialog` asks for a fresh code and the action is repeated once. A wrong code is a 401 from the server but does **not** end the session (only a real expiry does; covered by a test).
- **Every write goes through `ReasonDialog`:** labelled textarea (5-500 characters, checked before sending), the server's error shown in the dialog, focus trapped and returned (the shared `Dialog`). The reason is internal and goes to the audit log; where the text reaches the seller or the user (warn, needs-info, hide listing) the field says so in its label.
- **Role-based UI is a convenience, not security.** The navigation and buttons come from `GET /admin/auth/me` (`permissions`); a role without a permission never sees the control, and typing a URL shows "You don't have access to this page" without requesting the data. The server still refuses everything (E2E checks both).
- **Personal data masked by default.** Lookups render what the server returns (masked); "Reveal personal data" opens a dialog that needs a ticket-style reason, shows a visible notice that the view was audited, and is only offered to roles with the reveal permission.
- **Client idle timeout (12 min)** signs out and says why; the server enforces 15 minutes and an absolute lifetime too.
- **Charts are never the only way to read data.** The dashboard's 14-day bar chart is an inline SVG with an `aria-label` summary and a "Show the numbers as a table" disclosure; colours are tokens and the legend names each series.
- **Tables** (`Table` component) are keyboard-focusable scroll regions with a caption and column headers; on a phone they scroll inside their own box (the page itself never scrolls sideways; the `sr-only` helper text inside them is positioned relative to the box for that reason). Button names with context use a visible label plus an `sr-only` suffix with a real space before it.
- **Design system reuse:** `Button`, `Field`, `PasswordField`, `Alert`, `Dialog`, `ThemeToggle`, tokens from `styles.css`; `admin.css` only adds layout (`adm-` prefix). Light/dark through the same tokens, 44 px targets, visible focus, `prefers-reduced-motion` untouched.
- **Seller field editor:** an ordered list of questions (move up/down, add, remove; the certificate upload field is locked), branch parents limited to earlier yes/no or choice questions, and a branching preview driven by the server's own rules (`/settings/seller-fields/preview`).

## Local delivery (workstream L)

Backend contract and privacy rules: `docs/LOCAL-DELIVERY.md` in the backend repository. Code: `src/delivery/**`; tests `src/delivery/*.test.ts(x)` (Vitest + MSW) and `e2e/delivery.spec.ts` (real backend, axe, mobile viewport for the driver).

* **Routes:** `/delivery` (dispatch board, sidebar "Local delivery"), `/settings/delivery` (Owner/Admin edit, others read), `/driver` (the driver app), plus a tracking panel in the order detail (`LocalTracking`).
* **Driver role is default deny in the UI too:** `RequireAuth` sends a Driver anywhere except `/driver` (and security settings) to `/driver`; `Home` does the same. The server answers 403 for everything else, so this is only the friendly half.
* **Driver app = one screen, big targets:** route list -> stop view -> a form. 56 px buttons, `min-height: var(--target)` fields, one-handed layout, no hard-coded colours (design tokens only), `dr-*` classes in `src/delivery/driver.css`. PWA: `public/driver.webmanifest`, `public/driver-icon.svg`, `public/driver-sw.js` (shell cache only; API calls are never cached), registered in production builds with scope `/driver`.
* **Offline queue (`queue.ts`):** every action is written to the queue first (localStorage for the item list, IndexedDB for photo blobs with a memory fallback) and sent in order: start route, photo uploads (idempotent on a client id), then events carrying a client event id and the time they happened. Network errors, 5xx, 408 and 429 keep the item and stop the flush; any other server answer is final for that item and is shown to the driver ("N updates could not be saved") without blocking the rest. The UI is optimistic (the stop shows Delivered at once, with a "waiting to send" count) and re-reads the route after a successful flush.
* **Photos** are redrawn on a canvas (max 1600 px JPEG) before queueing: smaller uploads and no EXIF; the server strips metadata again.
* **Location sharing** needs an explicit "Allow sharing" (explained in plain words), runs only while a route is active, can be paused or stopped at any time, and posts about every 45 s.
* **Details hidden after completion:** the stop view shows "This stop is finished" and no address/contact (the API sends none).
* **Inputs that reformat while typing** (money, postcode lists) keep their own text and commit the parsed value (`Parsed` in `DeliverySettings.tsx`): found by a test that typed "5.50" and got 55000 cents.
* **Settings tab "Local delivery":** time zone, cutoff, lead time, days ahead, zones (fee, free-over, minimum, postcodes with `112*`, radius + origin) and windows (from/to, capacity, weekdays).
* **Dispatch board:** day picker, window capacity chips with "Nearly full / Full", deliveries grouped by window with Late and "Needs attention" highlights, assign / unassign (a failed stop is unassigned, then assigned again), per-route optimize / reassign / print sheet; refreshes every 30 s (no live map in v1).

## Shipping & tracking (workstream K)
Code: `src/shipping/**` (`api.ts`, `ShippingSettings.tsx`, `BuyLabel.tsx`, `OrderShipping.tsx`, `format.ts`, `shipping.css`), hooks into `orders/Dialogs.tsx` (ship dialog), `orders/OrderDetail.tsx`, `orders/OrdersList.tsx` and the Settings tabs. Backend contract, flows and money: backend `docs/SHIPPING.md`.

### Pages and flows
- **Settings -> Shipping** (`/settings/shipping`, a lazy tab next to Brands/Notifications): ship-from addresses (verified / not verified chip, default, edit, remove), package presets, shipping rate profiles (zones, flat or by-weight price per speed, free-shipping threshold) and "Handling time and returns" (handling days, label format, return address). Owners and Admins edit; everyone else sees the same page read-only with a plain explanation (controls are hidden, the server stays the authority).
- **Ship dialog** gains the tabs **Buy label** and **Enter tracking manually** (`TabList`). The item quantities stay above the tabs, so a partial shipment is the same for both ways. Buy label: ship-from + package (preset or custom size) + optional weight -> "Get shipping rates" -> radio list of services with price, estimated delivery and a **Recommended** chip (cheapest that arrives by the deliver-by date) -> "Buy label · $x". Customs fields appear only when the destination country differs from the ship-from country. An unverified buyer address shows a warning with **Ship anyway** and a required reason (sent with the purchase). After buying, the dialog shows tracking number, **Print label** (opens the file in a new tab through a blob URL, because the file needs the bearer token; ZPL is downloaded), Download, and "print the packing slip together".
- **Safe buying:** one `idempotencyKey` per quote (regenerated when the rates change), so a double click or retry returns the first purchase; `rate_expired` says "we are not charging you" and clears the rates; the spend-limit error is shown as the server words it. The dialog keeps showing the label it just bought even though the page behind reloads the order as fully shipped (the dialog freezes the item list it opened with).
- **Without a ship-from address** the dialog opens on the manual form with a hint and a link to Settings -> Shipping (the established flow is unchanged until a seller opts in); the Buy label tab then explains what is missing.
- **Order detail:** a "Tracking and labels" card per order: a delivery-problem banner with "Mark as handled", each shipment's timeline (newest first, status chip, estimate, "updates arrive automatically"), the label row (Print, Download, **Void label** with a confirmation that says the money returns only when the carrier confirms), and return parcels. The shipments list shows the tracking chip and the label cost. Approved returns get **Send a prepaid return label** (the seller pays; customs fields appear only if the server asks); when the return parcel is delivered the card says "Return arrived - inspect the items and mark the return as received" next to the existing **Mark as received** button (never automatic).
- **Orders list:** a tracking chip per order (`In transit`, `Delivery problem`, ...), a "Delivery progress" filter (in transit / delivery problem / delivered), dashboard tiles **Labels to print** and **Delivery problems**, and bulk **Buy labels** for the selected orders (package, recommended or cheapest, optional weight; per-order results, unverified and international orders are reported as not bought).
- Tracking statuses are shown in plain words (`Label created`, `In transit`, `Out for delivery`, `Delivered`, `Ready for pickup`, `Returning to sender`, `Delivery problem`); colour is never the only signal (the word is always there). Notification settings gain "Delivery problems" (Owners always get the email).

### Decisions
- Reused `Dialog`, `TabList`, fields and chips; styles in `shipping.css` use tokens only (no hard-coded colours; the restyle owns the palette). `ShippingSettings` imports `products/products.css` like Payments does, because the dialog sizing/scroll rules (`.pdialog`) live there and Settings does not load the product routes (found by the E2E: a tall dialog had an unreachable Save button).
- New order fields are optional in the TypeScript types (`trackingStatus`, `needsAttention`, `returnShipments`, `actions.buyLabel`, ...), so older fixtures keep working.
- Server error details for labels are read from `error.errors` as an object (`errDetail`), never through `fieldErrors()` (which expects arrays).

- Small ones: the "ship anyway" reason is required with its error on the field; Refresh rates is disabled while buying (it would rotate the idempotency key); voiding and removing addresses/packages/rate profiles ask for a destructive confirmation; the "enter tracking yourself" link became a 44px button; the warning dot uses `--warn`; "Clear filters" also shows for the delivery-progress filter.
